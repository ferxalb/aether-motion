# Native 3D scenes (`data-hf-3d`)

AETHER Motion 0.2 draws low-poly 3D geometry natively: a scene graph of meshes, lights, and one
camera inside an ordinary 2D element. The scene is rasterized into that element's box at output
resolution, so it composes with everything else the renderer does: clip timing, fades, 2D cameras and
parallax, 2.5D spaces, filters, bloom, masks, motion blur, transitions, and native MP4 export.
Output is a pure function of time. The CPU rasterizer is the default and the reference, and it is
deterministic across threads, render segments, and CPUs. An optional wgpu backend draws the same
triangles on a GPU.

See [Lighthouse Isle](../examples/lighthouse-isle-3d.html) for a continuous crane and orbit around
a rotating volumetric beacon. Its lantern mullion casts a shadow through the shaft during the sweep.

See [native physics and volumetric lighting research](native-physics-and-volumetrics.md)
for proposed extensions to the renderer.

## Quick start

```html
<div id="world" class="clip" data-start="0" data-duration="6" data-track-index="1"
     data-hf-3d data-hf-3d-antialias="3"
     style="position: absolute; left: 0; top: 0; width: 1920px; height: 1080px">
  <hf-light type="ambient" color="#6a78b0" intensity="0.5"></hf-light>
  <hf-light type="directional" color="#ffd9b0" intensity="1.2" direction="0.5 0.8 -0.4"></hf-light>
  <hf-camera position="0 -300 1200" target="#hero"
    data-hf-keyframes='[{"at":0,"x":-600},{"at":6,"x":600,"easing":"smooth"}]'></hf-camera>
  <hf-mesh shape="plane" size="4000 4000" color="#2a3350"></hf-mesh>
  <hf-node id="hero" position="0 -100 0"
    data-hf-keyframes='[{"at":0,"rotateY":0},{"at":6,"rotateY":180,"easing":"ease-in-out"}]'>
    <hf-mesh shape="box" size="160 200 160" color="#d08c5a"></hf-mesh>
    <hf-mesh shape="sphere" radius="70" detail="2" color="#7fb3d5" position="0 -170 0"></hf-mesh>
  </hf-node>
</div>
```

Close every `<hf-*>` tag explicitly (`<hf-mesh ...></hf-mesh>`): HTML has no self-closing custom
elements.

## Coordinates and transforms

The scene shares the conventions of CSS and 2.5D spaces:

- The origin is the center of the host element's box. **x** points right, **y** down, and **z**
  toward the viewer. "Up" is -y, so a floor at height 100 px below the origin is at `y = 100`.
- Units are CSS px of the host element. The default camera sits 1000 px in front of the origin and
  looks along -z with a 1000 px focal length, so the plane z = 0 maps one to one onto the element's
  box (like CSS `perspective: 1000px` and a 2.5D space at rest).
- A node's local transform is CSS `translate3d(x, y, z) rotateY() rotateX() rotate() scale3d()`:
  `position="x y z"`, `rotation="rotateX rotateY rotate"` (degrees, CSS senses), and `scale="s"`
  or `scale="sx sy sz"` (negative values mirror; the winding is corrected so mirrored solids stay
  closed). Children compose with their parents.
- The front of a triangle `(a, b, c)` is the side its normal `(b - a) x (c - a)` points to; with y
  down, that is clockwise winding as seen on screen. Every primitive faces outward.

## The host element

`data-hf-3d` marks a sized, non-root `<div>` (or `<section>`, `<main>`, `<article>`) as a viewport.
It is a normal clip: it takes `class="clip"` timing, `data-track-index`, fades, keyframes, CSS
animation, filters, `data-hf-bloom`, `data-hf-motion-blur`, transitions, `overflow`, `clip-path`,
masks, and plane attributes inside a `data-hf-space`. Its own CSS background, border, and shadows
draw behind the scene; the scene fills the padding box and is clipped to it. Where nothing is drawn,
the viewport is transparent.

| Attribute | Meaning |
| --- | --- |
| `data-hf-3d` | Marker (no value). |
| `data-hf-3d-antialias` | Supersampling per axis, 1 to 4 (default 2): each output pixel averages `n^2` samples. |

The viewport accepts `<hf-node>`, `<hf-mesh>`, `<hf-light>`, `<hf-camera>`, and direct-child
`<hf-body>` and `<hf-hinge>` elements, and an optional `<hf-beam>`. Text and any other element are errors. `data-hf-3d` cannot share an element with
`data-hf-space`, `data-hf-camera`, `data-hf-shots`, `data-hf-split`, `data-hf-counter`, or
`data-hf-captions` (wrap it instead).

## Nodes

Every `<hf-*>` element is a node with an optional `id` (unique in the scene). The attributes for
each type are described below. Unknown attributes are errors. `data-var-if` removes a node (and
its children) when its test is false, as for 2D elements; light `color` takes `var()` like meshes.

### `<hf-node>`: groups

An empty transform that its children inherit, for pivots and orbits.

### `<hf-body>`: rigid-body physics

Add fixed, dynamic, and kinematic bodies directly inside a `data-hf-3d` viewport. A body has one centered
collider and draws through its children. Use a fixed collider for a floor or obstacle. Match the
dimensions of the collider and its child mesh so contact occurs at the visible surface.

```html
<hf-body id="floor" type="fixed" shape="box" size="600 20 400" position="0 80 0">
  <hf-mesh shape="box" size="600 20 400" color="#29303b"></hf-mesh>
</hf-body>
<hf-body id="ball" type="dynamic" shape="sphere" radius="22" position="0 -110 0"
         velocity="35 0 0" restitution="0.45" ccd>
  <hf-mesh shape="sphere" radius="22" detail="3" color="#f7b465"></hf-mesh>
</hf-body>
```

| Attribute | Values |
| --- | --- |
| `type` | Required. `fixed`, `dynamic`, or position-keyed `kinematic`. |
| `shape` | Required. `box` with full `size="width height depth"`, `sphere` with `radius`, or `cylinder` / `cone` with `radius` and `height` (y axis, centered; a cone's base is at the bottom). Each dimension is 1–100,000 scene px. The collider is round, so a low-segment child mesh sits slightly inside it. |
| `position`, `rotation` | Initial body pose in scene px and CSS-axis degrees. Both default to zero. |
| `friction`, `restitution` | 0–1. Defaults are 0.5 and 0. Rapier averages each coefficient across the two touching colliders. |
| `mass` | Dynamic only. 0.01–10,000 kg, default 1. |
| `velocity`, `angular-velocity` | Dynamic only. World-axis initial velocity in scene px/s and degrees/s, respectively. Each component defaults to zero. |
| `ccd` | Dynamic only. Continuous collision detection for fast bodies. Bare `ccd` or `ccd="true"` enables it, and the default is false. |
| `linear-damping` | Dynamic only. Linear damping coefficient in 1/s, 0–100, default 0. |
| `angular-damping` | Dynamic only. Angular damping coefficient in 1/s, 0–100, default 0. |

The simulation uses 100 scene px per meter and gravity of 981 px/s² toward positive y. It bakes
120 ticks/s from the viewport's start, then interpolates neighboring poses at render and shutter
times. The output frame rate and render order have no effect on the bake. A viewport supports up
to 128 bodies, 60 seconds, and 16 MiB of packed pose samples. `check` reports the bodies, tick
rate, tick count, and pose bytes in `scenes3d[].physics`. Motion and scale on visual children use
ordinary 3D animation. A kinematic body's keys animate its `x`, `y`, `z`, `rotateX`, `rotateY`,
and `rotate` channels with `linear` or `smooth` easing. Each step targets the authored pose at
the end of that tick. The kinematic collider can push dynamic bodies while following its track.

Run `aether-motion inspect <file>` to read each dynamic body's requested XYZ launch vectors,
the velocity returned by Rapier after the first solver step, and the first tick when an
over-limit request is evaluated. Tick 0 is the initial pose and tick 1 ends 1/120 s into the
viewport. The linear cap is 40,000 px/s and the angular cap is about 5,400 degrees/s. Both are
magnitude limits. Gravity, damping, and contacts can also affect the tick-one result.
`check` and `aether_check` expose the same data at `scenes3d[].physics.bodies[].launch`, with
`requested`, `actual`, `actualTick`, `limit`, `unit`, and `firstTickAffected` for `linear`
and `angular`. A null `firstTickAffected` means the authored vector was within its cap.

### `<hf-hinge>`: revolute joint

Add an empty, direct-child `<hf-hinge>`. Set `body-a="#mount"` and `body-b="#lamp"` to two
body IDs in the viewport, with at least one dynamic body. `anchor-a` and `anchor-b` are XYZ
positions in each body's local px and default to `0 0 0`. Place both anchors at the same world
point in the initial pose. `axis` specifies the same direction in each body's local frame
(default `0 0 1`), so align those directions in the initial pose. Optional `limits="-70 70"`
set increasing relative angles strictly within −180° and 180°. Connected bodies skip mutual
collision. A viewport can have up to 128 hinges. `check` lists authored hinges under
`scenes3d[].physics.hinges`.

[Hinged lamp](../examples/hinged-lamp.html) shows a kinematic strike at 0.80 s and a hinge
carrying a light shaft across a column. A one-second segment split lands during the swing.
To reproduce the fixture's export check, render the full 640×360 composition at 30 fps, then
independently render `--segments 0..1` and `--segments 1..3` to two `.aseg` files with the same
options. Assemble them with `render --parts` and compare the two MP4s byte for byte.

### `<hf-mesh>`: geometry

| `shape` | Size attributes (px) | Triangles |
| --- | --- | --- |
| `plane` | `size="width depth"` (default 200 200); lies in x-z, facing up (-y) | 2 |
| `box` | `size="w h d"` (default 100 100 100) | 12 |
| `pyramid` | `size="w h d"`: square base `w x d` at the bottom, apex at the top | 6 |
| `cone` | `radius` (50), `height` (100), `segments` (3 to 128, default 16); base at the bottom | `2 * segments - 2` |
| `cylinder` | `radius`, `height`, `segments` | `4 * segments - 4` |
| `sphere` | `radius` (50), `detail` (0 to 4, default 1): an icosphere | `20 * 4^detail` |
| `custom` | `vertices="x y z, x y z, ..."` and `indices="a b c, ..."`: an indexed triangle mesh | as given |

Primitives are centered on their bounding box. Each face has its own vertices, as flat shading
needs, and its own UVs; custom meshes are drawn exactly as indexed. Size attributes that do not apply to a shape are
errors.

Materials:

| Attribute | Values |
| --- | --- |
| `color` | Any supported CSS color (default `#c8c8c8`), including `var(--name)` of the host's custom properties (themes and composition variables); alpha is ignored (meshes are opaque). |
| `material` | `lambert` (default): flat diffuse shading, one value per face (per sample with a look). `unlit`: the base color, unaffected by lights. |
| `specular`, `shininess` | Lambert only. `specular` 0–1 (default 0) adds a white Blinn-Phong highlight per face, with exponent `shininess` 1–512 (default 32). |
| `cull` | `back` (default): faces seen from behind are skipped. `none`: both sides draw; the back is lit as if its normal were flipped. |

### Textures, UVs, and shaders

Any `<hf-mesh>` can take a **look**: image textures, normal and emissive maps, smooth shading,
alpha cutouts, and a named shader. A mesh with a look is shaded per sample (per supersample) by the
CPU rasterizer; a mesh without one keeps the flat path. The two mix freely in one scene and share
one depth buffer.

```html
<hf-mesh shape="box" size="720 300 60" texture="assets/brick.png"
         normal-map="assets/brick-normal.png" uv-scale="3 1.25" specular="0.15"></hf-mesh>
<hf-mesh shape="sphere" radius="90" detail="3" smooth shader="toon" shader-steps="4"
         color="#e46a3c"></hf-mesh>
<hf-mesh shape="box" size="110 110 110" shader="dissolve" shader-color="#ff7a1a"
         data-hf-keyframes='[{"at":0,"progress":0},{"at":3,"progress":1,"easing":"smooth"}]'></hf-mesh>
```

See [Textured and shaded 3D](../examples/textured-shaded-3d.html).

**UVs.** Every primitive has UVs: `u` runs left to right and `v` top to bottom of the image, so
`uv = (0, 0)` is the top-left texel. A plane maps its whole rectangle seen from above; each face of
a box (and the caps and faces of a pyramid) maps its own 0 to 1 range, upright on every side;
cylinders and cones wrap `u` around the y axis from +x (counter-clockwise seen from above, with `v`
from top to bottom); spheres use longitude and latitude with the north pole (-y) at the top. A
`custom` mesh needs `uvs="u v, u v, ..."`, one pair per vertex, whenever its look reads UVs.

**Textures.** PNG, JPEG, and WebP files, resolved against the composition's folder like `<img>`.
Files are decoded once per scene, filtered trilinearly with a mip chain built at load (color in
linear light), and limited to 4096 px on an edge, 16 megapixels each, 16 files, and 32 megapixels in
total. A texture file is a parse dependency, so `preview` reloads when it changes.

| Attribute | Values |
| --- | --- |
| `texture` | Base color image (sRGB), multiplied by `color` (default `#c8c8c8`, so set `color="#fff"` to show the image as it is). |
| `normal-map`, `normal-strength` | Tangent-space normal map (linear; green points up in the image, the OpenGL convention) and its strength 0–4 (default 1). Tangents come from the UVs. |
| `emissive-map`, `emissive`, `emissive-intensity` | Light added after lighting: an sRGB image and/or a CSS color, scaled by intensity 0–16 (default 1). With only a map the color is white. |
| `uv-scale`, `uv-offset`, `uv-scroll` | `"u v"` or one number: tiling, shift, and travel per second (animates the look). `uv-scale` is not 0. |
| `uv-wrap` | `repeat` (default) or `clamp`. |
| `alpha-cutoff` | 0–1. Samples whose texture alpha is below it are not drawn (foliage, fences); needs a texture with transparent pixels. There is no partial transparency. |
| `smooth` | Interpolated vertex normals (welded by position) instead of one normal per face. Right for spheres and cylinders; a smooth box shades like a pillow. |
| `shader`, `shader-*` | A named shader, below. Parameters without `shader` are errors. |

Lights apply per sample, including point lights, `specular`, and `material="unlit"` (the texture and
emission only). Whether a light is blocked (`shadows="true"`) is decided once per triangle, at its
center, so shadows on textured meshes are as coarse as the mesh.

**Shaders.** Closed-form functions of UV, world position, normal, and the clip time: they are not
user code, so a frame stays a pure function of time and is identical on every CPU. Colors are CSS
colors (`var()` included). Defaults are listed per shader.

| `shader` | Effect | Parameters (default) |
| --- | --- | --- |
| `toon` | Diffuse light cut into flat bands. Needs `material="lambert"`. | `shader-steps` 2–16 (3) |
| `rim` | Glow where the surface turns away from the camera. | `shader-color` (blue), `shader-strength` (1), `shader-power` (3) |
| `hologram` | Dark body with moving scanlines, a flicker, and a rim glow. | `shader-color` (cyan), `shader-scale` lines per 100 px (8), `shader-speed` px/s (60), `shader-strength` (1), `shader-power` (2) |
| `checker` | Two colors in alternating UV cells. Replaces the material color. | `shader-color`, `shader-color-2`, `shader-scale` cells per UV unit (8) |
| `stripes` | Two colors in alternating stripes along `u`. Replaces the material color. | as `checker` |
| `gradient` | `shader-color` at the top of the image to `shader-color-2` at the bottom. | colors |
| `noise` | Two colors blended by fractal noise of the world position, optionally drifting. | colors, `shader-scale` per 100 px (3), `shader-speed` (0) |
| `water` | Animated ripples bend the normal; a fresnel blend between a deep and a shallow color. Pair with `specular`. | colors, `shader-scale` (3), `shader-speed` (1), `shader-strength` slope (0.15), `shader-power` (3) |
| `dissolve` | Noise eats the surface away as `progress` rises, with a glowing edge. | `shader-color` edge, `shader-scale` (3), `shader-strength` edge width (0.08), `shader-progress` 0–1 |

A texture and a procedural shader multiply. `progress` is also a keyframe channel of the mesh
(`"progress": 0` to `1`), and only `dissolve` accepts it. Shaders that move (`hologram`, `water`,
`noise` with a speed, `uv-scroll`, `progress` keys) make the scene animate for motion blur and the
identical-frame shortcut.

**Backends.** Looks are drawn by the CPU rasterizer, as `<hf-beam>` is. With `--3d-backend gpu`,
`auto`, or `cuda`, scenes with a look draw on the CPU and `check` reports the reason in
`gpuFallback`; `--require-gpu` fails with it. `check` lists each mesh's look under
`scenes3d[].meshes[].look` (texture sizes, shader, smooth, cutoff, whether it animates).

**Cost.** Shading runs for each sample that passes the depth test, so a textured mesh costs more
than a flat one in proportion to covered pixels x `antialias`². Keep full-frame textured planes at
`data-hf-3d-antialias` 2 and give small props the detail.

### `<hf-light>`: lighting

| Attribute | Meaning |
| --- | --- |
| `type` | `ambient` (light from everywhere), `directional` (parallel light), or `point` (omnidirectional). |
| `color` | Default white. |
| `intensity` | 0 to 16 (default 1); keyframable as `intensity`. |
| `range` | Point only: px at which the light reaches zero (1–100,000, default 1000). Falloff is a windowed inverse square, `(1-(d/range)^4)^2 / (1+(4d/range)^2)`, so intensity is 1 at the light. A point light sits at its node's world position. |
| `shadows` | `true` lets scene meshes block a directional or point light (hard shadows, tested at each face centroid). Default false. A scene with a shadowing light may hold at most 4,000 triangles; at most 8 point lights. |
| `direction` | Directional only: `"x y z"` the light travels along (default `0 1 0`, straight down), turned by the node's rotation and its parents'. |

A Lambert face is `base x (sum of ambient + sum of directional x max(0, n . -direction))`, computed
in linear light and encoded to sRGB. A scene without lights uses a default rig: white ambient at
0.35 and a white key at 0.9 travelling `0.45 0.8 -0.4`. At most 8 directional lights.

### `<hf-beam>`: bounded light shaft

Place one empty `<hf-beam>` anywhere in the viewport hierarchy, including under a rigid body.
Its position is the tip of a softly feathered cone. Set `direction` (default `0 1 0`) in
local axes, `length` (default 200 px), end `radius` (default 40 px), `density` (default 0.02
per scene px), and `color` (default white). Length and radius are 1–10,000 scene px and
density is 0–1. The hierarchy turns the direction, and length and radius stay in scene px.
An optional `occluder="#column"` names one box mesh that shadows the shaft. Every opaque mesh
occludes the shaft from the camera according to its rendered depth. Ordinary surface
illumination uses the viewport's ambient and directional lights.

The CPU clips each camera ray to the cone and the first opaque surface before sampling the shaft.
It composites in linear light within the 3D viewport and exports through the sRGB viewport layer.
A composition with a shaft selects the CPU before rendering and fails `--require-gpu` at setup.
`check` lists geometry and occluder settings in `scenes3d[].beams`.

### `<hf-camera>`: the view

At most one per scene; without one, the default camera above is used. The camera is a node, so it can
sit inside a rotating `<hf-node>` for an orbit or crane.

| Attribute | Meaning |
| --- | --- |
| `position` | Eye position (default `0 0 1000`, or `0 0 <perspective>`). |
| `projection` | `perspective` (default) or `orthographic`. |
| `perspective` | Focal length in px (50 to 100000, default 1000): a point this far from the eye is drawn at its own size. |
| `fov` | Instead of `perspective`: the vertical field of view in degrees (1 to 170), relative to the viewport height. |
| `zoom` | Lens multiplier (0.05 to 50, default 1); for orthographic cameras, px per world px. |
| `yaw`, `pitch`, `roll` | Degrees, with the 2.5D camera's senses: positive yaw pans right, positive pitch tilts up, positive roll turns clockwise. |
| `target` | `"#node-id"` (follows that node's world origin) or `"x y z"`. The camera aims at it with a level horizon; `yaw` and `pitch` then turn it away from the aim around world-vertical and its own horizontal axis. |
| `near`, `far` | Clipping distances in px (defaults 10 and 50000). |

Keyframe channels: `x`, `y`, `z` (position), `yaw`, `pitch`, `roll`, and `zoom`. A camera does not
take `rotation` or `scale`.

## Animation

`data-hf-keyframes` on any node is a JSON array of `{"at": seconds, ...channels, "easing": name}`.
`at` counts from the host clip's start (0 to 3600, strictly increasing).

| Node | Channels |
| --- | --- |
| `hf-node`, `hf-mesh`, `hf-beam` | `x`, `y`, `z`, `rotateX`, `rotateY`, `rotate`, `scale` (all three axes), `scaleX`, `scaleY`, `scaleZ` |
| Kinematic `hf-body` | `x`, `y`, `z`, `rotateX`, `rotateY`, `rotate` with `linear` or `smooth` |
| `hf-light` | the node channels plus `intensity` |
| `hf-camera` | `x`, `y`, `z`, `yaw`, `pitch`, `roll`, `zoom` |

A channel omitted at a keyframe keeps the previous keyframe's value; before the first keyframe
that names it, it holds the static attribute value. The easing of a keyframe shapes the segment that
ends there: every `data-hf-keyframes` name (`linear` by default, `ease-*`, `cubic-bezier()`,
`spring()`) and `smooth` (monotone cubic Hermite through the keys, continuous velocity, as camera
rigs use). The first and last values hold outside the keyed interval.

## Visibility

- **Near and far clipping**: triangles are clipped in clip space against the near and far planes
  (and a guard band around the viewport), so geometry that passes the camera is cut cleanly.
- **Back-face culling**: per material (`cull`).
- **Depth testing**: per sample, with a reversed `f32` depth buffer (1 at the near plane, 0 at the
  far plane, linear in screen space). A sample keeps the first triangle that is strictly nearer, so
  coplanar ties resolve in document order. Intersecting meshes are resolved per sample.

## Rendering backends

- **CPU (default)**: fixed-point edge functions (1/256 sample precision, top-left fill rule) in 64 px
  tiles. Only one tile's samples are held at a time (at most 512 KiB at 4x4 supersampling). Each pixel
  resolves to the mean color of its covered samples, with the covered share as alpha. It is
  deterministic across thread counts, segment splits, and CPUs.
- **Looks**: meshes with textures, shaders, or smooth shading are shaded per sample by the CPU
  rasterizer, which every backend request falls back to for such scenes (see
  [Textures, UVs, and shaders](#textures-uvs-and-shaders)).
- **GPU**: standard builds and Cargo installs include wgpu (Vulkan, Metal, or DX12). Pass
  `--3d-backend gpu` to `render` or set `AETHER_3D_BACKEND=gpu` to request it. Use `auto` to
  select it when available, or `cpu` to explicitly select the CPU. A custom CPU-only build can
  use Cargo's `--no-default-features`. The GPU
  draws the same shaded triangles with the same clip matrix, reversed depth, and integer resolve, and
  reads the resolved rows back. If the build has no GPU feature, no adapter initializes, or any GPU
  call fails, scenes are drawn on the CPU: `render` prints a note on stderr, `check` reports
  `"backend"` and `"gpuFallback"`, and the process stays on the CPU so a render never mixes backends.

- **CUDA** (opt-in, Linux, NVIDIA): `--3d-backend cuda` (or `AETHER_3D_BACKEND=cuda`) in a binary built
  with `cargo build --release --features cuda`. It is never selected by `gpu` or `auto`. The host
  evaluates the scene and clips and snaps every triangle exactly as the CPU does; one kernel
  (`src/scene3d/cuda/raster.cu`) covers samples with the same integer edge functions and top-left
  rule, depth-tests them in draw order with the same reversed `f32` depth, and resolves each pixel
  with the CPU's integer mean. Only triangle rasterization, depth, and resolve run on the GPU; the
  rows then go through the same sink as CPU rows, and 2D composition, effects, audio, and encoding
  are untouched. The binary loads `libcuda.so.1` at run time (no CUDA link dependency) and looks for
  the precompiled kernel in `AETHER_CUDA_KERNEL_DIR`, else `cuda/` or the folder next to the
  executable. Build the kernel with `python tools/build_cuda_kernel.py OUT_DIR` (needs only the
  `nvidia-cuda-nvrtc-cu12` wheel): it writes `raster_sm86.cubin` for the A10 and `raster_compute75.ptx`,
  portable PTX the driver compiles for newer GPUs (Ada, Hopper, Blackwell), built with
  `--fmad=false` so depth is evaluated as on the CPU. Any failure falls back to the CPU like
  `gpu`, or aborts the render in strict mode.

`--require-gpu` (with `--3d-backend gpu` or `cuda`) is strict mode for exports that must not use the CPU
rasterizer: it needs a Vulkan adapter from NVIDIA (`gpu`) or a CUDA device (`cuda`) for the backend
asked for, any GPU failure aborts the render with an error instead of falling back, and the render
prints `AETHER_3D_PROOF {...}` on stderr with the backend, adapter, API and vendor, the number of GPU
draws, and the number of fallbacks. A `cuda` proof also carries a `cuda` object: driver version,
compute capability, device UUID, the kernel artifact and whether the driver JIT-compiled it,
`launches` (kernels that ran to completion and were read back), and summed upload, kernel, and
readback times. Without the flag nothing changes.

### CUDA parity

The CUDA backend does the CPU's arithmetic, so its output is expected to be byte-identical, not
merely close. Measured on an NVIDIA A10 (driver 610.57.04, compute capability 8.6, NVRTC 12.6,
precompiled `sm_86` cubin): `examples/cuda-parity-3d.html` (overlapping solids, a depth tie, geometry
clipped by the near plane, 4x4 antialiasing) and frames 60 and 200 of the original Lighthouse Isle
scene at 1080p each differ from the CPU in 0 pixels. The current Lighthouse Isle scene uses the
CPU shaft renderer. At 1080p with 3x3 supersampling the kernel took about
9.7 ms per frame and the readback of the 8.3 MB RGBA region 3.9 to 5.4 ms; the whole frame still
took about 212 ms (the CPU rasterizer's total was 213 ms), because 2D composition and the rest of
the pipeline dominate there. The portable PTX path is not yet measured.

### GPU tolerance

GPU output is not byte-identical to the CPU. The two differ only where the hardware rasterizer
covers or depth-tests a sample differently from the fixed-point one: triangle edges and depth ties.
The documented tolerance, checked by `tests/scene3d_gpu.rs` per frame, is:

- mean absolute difference (largest channel per pixel) under 0.25 levels of 255, and
- at most 0.2% of pixels more than 2 levels apart.

Measured on Mesa lavapipe (Vulkan, software): 0 to 6 of 129,600 pixels more than 2 levels apart at
480x270, mean 0.0004 levels or less. On the original 1080p Lighthouse Isle fixture, at most 20 of
2,073,600 pixels differ by more than 1%, all on edges. Repeated GPU draws on one device are identical. Use the CPU backend
when byte-identical exports matter (distributed parts, regression baselines).

## Composition and effects

- The scene is drawn at the element's on-screen size: 2D camera zoom, CSS `scale`, `--scale`, and
  `--size` raise its resolution instead of scaling a bitmap.
- Inside a 2.5D space, the viewport is a flat plane like any other element (tilt it, move it in depth,
  warp it). The 3D camera is independent of the space camera.
- Root shutter motion blur and `data-hf-motion-blur` treat scene animation as movement, and size
  their sample counts from the on-screen travel of mesh bounding boxes.
- Effect layers (`filter`, `data-hf-bloom`, transitions, and others) draw their subtree twice (on
  black and on white). The second draw replays the first from a one-entry memo of the resolved region
  (at most 64 MiB), with identical pixels.
- `check` reports each scene under `scenes3d`: timing, `antialias`, node and triangle counts,
  meshes (shape, triangles, material, cull), lights, camera (projection, focal or fov, near, far,
  target), whether it animates, the backend, and any GPU fallback reason.

## Limits

| Limit | Value |
| --- | --- |
| Nodes per scene | 4096 |
| Triangles per scene (all meshes, before culling) | 100,000 |
| Vertices / triangles per mesh | 65,536 / 100,000 |
| Directional lights per scene | 8 |
| Coordinates and sizes | within 1,000,000 px |
| Rotations / keyframed angles | within 100,000 degrees |
| Scale | within 1000 (in magnitude) |
| Supersampling | 1 to 4 per axis |
| Texture files per scene / edge / texels per file / texels per scene | 16 / 4096 px / 16 M / 32 M |

## Not supported

These are explicit errors or simply absent in this release:

- PBR (metallic and roughness), environment lighting, and per-material transparency other than an
  alpha cutout (fade the whole viewport with `opacity` or `data-hf-fade-*` instead).
- Per-pixel shadows (shadows are per triangle), spot lights, global fog, user-written shaders, and
  GPU or CUDA drawing of textured and shaded meshes.
- glTF, OBJ, or any other model file (use `shape="custom"` with inline vertices and indices).
- Skeletal or morph animation (animated characters), joint motors, and deformable physics.
- More than one camera per scene, and 3D text (put text in 2D elements over the scene).
- `<hf-*>` elements outside a `data-hf-3d` host, and 3D content inside SVG.

## Performance

The cost is proportional to covered samples: `pixels x antialias^2 x overdraw`, plus a per-triangle
setup that is negligible for low-poly scenes. Measured on the example (2,594 triangles, a sea plane
covering most of the frame), one thread, per frame:

| `data-hf-3d-antialias` | 1080p | 4K |
| --- | --- | --- |
| 1 | 27 ms | 99 ms |
| 2 (default) | 37 ms | 151 ms |
| 3 | 61 ms | 244 ms |
| 4 | 95 ms | 340 ms |

See `BENCHMARK.md` for the full measurements, including exports and multi-thread peak RSS.
